The fastest honest test of Mercury is **parity plus speed**: run the same libraries and patients through Mercury and your current engine, and compare. This page gets you to a first result.

## Prerequisites

- **Docker** (to run the container) *or* the **Mercury binary** (to run it directly).
- The **CQL libraries** you already use — or their compiled ELM XML.
- A **FHIR patient bundle** and any value sets the measure under test needs.
- *Optional:* your existing reference stack, running, for a side-by-side comparison.

## Build the local image

Until your team has a published registry image, use the local image name `mercury:community` throughout these docs:

```bash
docker build -t mercury:community .
```

If you later pull a published image such as `ghcr.io/EXAMPLE/mercury:2.1.0`, replace `mercury:community` consistently in the examples below.

## The happy path

<Steps>

1. **Start the server.**

   <Tabs>
     <TabItem label="Docker">
     ```bash
     docker run --rm \
       -p 8080:8080 \
       -v mercury-data:/var/lib/mercury \
       mercury:community
     ```
     </TabItem>
     <TabItem label="Binary">
     ```bash
     mercury serve --host 127.0.0.1 --port 8080
     ```
     </TabItem>
   </Tabs>

   Mercury exposes its routes under the base paths `/cqf`, `/api`, and `/fhir`. Confirm it's up:

   ```bash
   curl -fsS http://127.0.0.1:8080/api/health
   ```

   Example response:

   ```json
   {
     "status": "UP",
     "version": "2.1.0",
     "edition": "community",
     "packs": ["core"]
   }
   ```

2. **Load your data** — POST a FHIR bundle.

   ```bash
   curl -X POST http://127.0.0.1:8080/cqf/data/bundle \
     -H "Content-Type: application/fhir+json" \
     --data @patients.bundle.json
   ```

3. **Load your library** — CQL or ELM (returns `201`).

   ```bash
   curl -X POST http://127.0.0.1:8080/cqf/Library \
     -H "Content-Type: application/fhir+json" \
     --data @Test.Library.json
   ```

4. **Execute** — evaluate for a subject and expression (returns `200` with a `Parameters` resource).

   ```bash
   curl "http://127.0.0.1:8080/cqf/Library/Test/\$evaluate?subject=Patient/123&expression=InDenominator"
   ```

</Steps>

<Aside type="tip" title="Expected result">
A FHIR `Parameters` resource whose `evaluate` part lists each expression and its value — for example `InDenominator → "true"`.
</Aside>

## Fixture smoke test

The repository includes a fixture-based happy path under `examples/quickstart` and a Docker smoke script that builds `mercury:community`, starts the server, checks `/api/health`, loads the bundle and library, runs `$evaluate`, and cleans up:

```bash
scripts/quickstart_smoke.sh
```

The expected final line is `Quickstart smoke passed`.

## One-shot: the `run` command

Prefer a single command without starting the server? The CLI `run` command evaluates local artifacts in-process. Data is supplied **inline** and isn't persisted — ideal for quick checks and CI.

```bash
mercury run \
  --data bundle.json \
  --valueset valuesets.json \
  --operation Test:1.0.0:InDenominator \
  --cql Test.cql \
  --context patient-1 \
  --parameter "Measurement Period_start:2025-01-01:DateTime" \
  --parameter "Measurement Period_end:2026-01-01:DateTime"
```

See the difference between loading data ahead of time and passing it inline in [Loading data: preload vs inline](/loading-data).

To verify the binary edition without the startup banner:

```bash
mercury --no-banner edition
```

Community builds report `edition=community` and enable Core only by default. Interoperability and observability surfaces stay off unless explicitly enabled.

## What success looks like

- Mercury returns the **same population results** as your reference engine for the same libraries and patients.
- Your existing **MCT or harness runs unchanged** against Mercury's base URL.
- Evaluation **latency and throughput improve** measurably on *your* workload.
